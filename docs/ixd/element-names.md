# Element naming — one string, three places

|  |  |
| --- | --- |
| **Version** | 1.0 |
| **Decided** | 2026-07-29 |
| **Owner** | Charles (technical decisions). Customer-facing words and the PAGE vocabulary need the owners' sign-off. |
| **Review by** | **2026-08-05 — silence means adopted.** A rule that stays "Proposed" forever is not a rule; it is a discussion. |
| **Companion** | [frame-names.md](frame-names.md) names the *page*. This file names everything *inside* a page. One system, two chapters. |

Every visible piece of the storefront (section, image, button, price…) carries
one stable, human-readable name. The same string appears in **three** places:

| Where | How it looks |
| --- | --- |
| Figma layer panel | layer named `HOME-HERO-SHOP-BTN` |
| Code | `data-el="HOME-HERO-SHOP-BTN"` |
| Analytics | `[data-el$="-SECTION"]`, read at runtime by `components/Beacon.tsx` |

The string is never transformed between them. That is the whole value: the owner
can point at a thing, the designer can find it in Figma, and it can be grepped in
the repo — with one word.

⚠️ **`data-el` is an analytics handle, not a test handle.** This file used to
claim both. In reality the end-to-end suite selects by role and text — 183
`getByRole`, 172 `getByText`, **zero** `getByTestId` — which is the accessible
and generally recommended way to test. Only `tests/e2e/engagement-beacon.spec.ts`
asserts on `data-el`, because that attribute is the thing it is testing. Do not
start writing product tests against `data-el`: it would couple every test to a
string whose real job is to be an analytics dimension.

## Where the convention lives — corrected 2026-07-29

This file previously said the design team's `.xlsx` was the source and the
markdown a transcription of it. **That was backwards**, and it was the worst
structural problem in the convention: the declared source of truth was a binary
blob in a scratch folder, generated by a script, that nobody can diff, review or
merge.

| File | Role | Direction |
| --- | --- | --- |
| **this file** | **the convention** — grammar, rules, vocabulary, enforcement | master |
| [frame-names.md](frame-names.md) | the page-level chapter, plus the live rename worklist | master |
| [figma-naming-guide.md](figma-naming-guide.md) | verbatim archive of the guide received 2026-07-25 | frozen record — never edit it to change the convention |
| `temp/Figma_UI_Naming_Guide_GoldRose.xlsx` | a spreadsheet **exported for** the design team | generated |

> **Version-control the text; generate the binary. Never the reverse.**
> This holds beyond naming — it is why schemas live in migrations rather than in
> a database GUI, and why config lives in a repo rather than in a dashboard.

The vocabulary tables below are the **applied** set: the guide's words plus our
additions, minus our removals. The test parses them from this file.

## Grammar

```
PAGE - SECTION - [QUALIFIER] - TYPE  [-INDEX]
```

- Uppercase, hyphen-separated. No camelCase, no dots, no lowercase.
- `QUALIFIER` is optional — a FUNCTION verb (`SHOP`, `ADD-TO-CART`) or a
  descriptive noun (`PRODUCT`, `BENEFIT`, `EYEBROW`).
- `INDEX` only where the design fixes the count (see [Repeats](#repeats)).

```
HOME-HERO-SHOP-BTN            page  section  function  type
PDP-PRODUCT-TITLE             page  section            type
SHOP-PRODUCT-CARD             page  section            type
HOME-PROMISE-BENEFIT-CARD-2   page  section  noun      type  index
```

## Rules

### 1. Name the role, never the appearance or position

`HOME-HERO-SHOP-BTN`, not `GOLD-BUTTON` or `TOP-BUTTON`. The gold may go in a
redesign; the role won't. A name that describes styling dies at the next redesign
and takes every test and analytics event with it.

### 2. Repeats

**Fixed design repeats get an index.** The four Real Rose Promise tiles are part
of the design, not the data — they get `-1` … `-4`:

```jsx
data-el="HOME-PROMISE-BENEFIT-CARD-3"
```

**Data-driven lists do not get an index.** Every card in the `/shop` grid shares
one name; identity lives in a second attribute, so adding a product doesn't
renumber the map:

```jsx
data-el="SHOP-PRODUCT-CARD" data-key="Y-034"
```

### 3. Don't tag decoration

Background fills, gradient rects and spacer divs get no name. If nobody will ever
point at it, it doesn't need a handle.

Exception, by necessity: carousel dots are rendered as sibling `<div>`s with no
wrapper element, so they are indexed individually (`…-DOT-1` … `…-DOT-4`) rather
than sharing one group name. Adding a wrapper purely to hold a name would mean a
DOM change to pixel-locked code — not worth it.

### 4. Figma node ids stay in comments, not in the DOM

The existing `{/* 158:77 · … */}` comments already tie code to the Figma REST
data, and the import tooling reads source, not the rendered page. Don't add a
third attribute carrying the node id — it would ship to every visitor for no
runtime benefit.

### 5. Live database text uses the EXISTING `data-live-text` marker

⚠️ **Do not invent a new attribute for this.** `data-live-text` already exists
on 6 elements (`components/BuyButtons.tsx`, `app/products/[slug]/page.tsx`,
`app/shop/page.tsx`) and it is **load-bearing**: the pixel suite masks exactly
those boxes —

```ts
// tests/e2e/pixels.spec.ts, tests/e2e/stage9-live-data.spec.ts
mask: [page.locator("[data-live-text]")]
```

A second, parallel marker would be worse than none: the mask locator would catch
only one of them, and a live box tagged with the wrong marker would silently
start failing the pixel baseline whenever its content changed.

So a live box carries both — `data-el` to name it, `data-live-text` to mark it:

```jsx
<div data-el="PDP-PRODUCT-PRICE" data-live-text>{formatMoney(cents)}</div>
```

Why it matters beyond masking: the frames were sized around the mock's copy, and
live values can be longer. This already bit once — `/shop` card prices overlapped
their compare-at price because the Figma box was sized for `$219` and
`formatMoney` adds cents. The same risk is still latent on `/products/[slug]`
above `$1,000`.

**The homepage (A-1 … A-11) has no live boxes** — all its copy and prices are
literal strings from the design — so nothing there is marked.

### 6. Names are unique per page

Two elements answering to the same name make a selector ambiguous and a
conversation confusing. Guarded by a test (see below).

### 7. A shipped name is frozen

Once a name reaches a deployed build it stops being a label and becomes a
**data key**. `components/Beacon.tsx` selects `[data-el$="-SECTION"]` and stores
those strings as engagement dimensions — so renaming a section after it ships
does not rename anything. It **silently splits the metric in two**: half the
history under the old string, half under the new, with no error raised anywhere
and nothing in the interface to reveal it.

Renaming a live name is therefore a data migration, not an edit. It needs an
alias recorded in this file and a decision about the rows already collected.

> ⏳ **Engagement tracking is built but not deployed
> ([engagement-tracking.md](../features/backend/engagement-tracking.md)), so
> today every name is still free to change.** Finish naming before it ships.
> After that, this rule has teeth and renames get expensive.

## Enforcement

`tests/unit/element-names.test.ts` parses the vocabulary out of this file — so
the doc and the code cannot drift — and scans every `.tsx` under `app/` and
`components/`.

**Enforce hard where the set is closed; warn where it is open.** A check that
blocks the build every time someone adds a new kind of button will be worked
around, and a convention people work around is worse than no convention at all.

| Check | Target level | Today | Why |
| --- | --- | --- | --- |
| Format is `UPPERCASE-HYPHENATED` | fail | fail ✅ | closed by definition |
| Names are unique | fail | fail ✅ | a duplicate makes every selector ambiguous |
| PAGE word is a real page | fail | fail ✅ | closed set — there are only so many routes |
| SECTION word is known | fail | fail ✅ | closed per page; a new band is a real design change |
| TYPE / FUNCTION word is known | **warn** | fail ⚠️ | open-ended — a new kind of control should not block a build. Review new words monthly |

### Decided 2026-07-29, not yet implemented

**The PAGE vocabulary must be computed from `app/**/page.tsx`, not written by
hand.** It is already a derived list — every valid page word corresponds to a
route that exists on disk — so maintaining it manually only creates a way for it
to go stale. The test should read the route tree and build the list itself.

Two changes are decided but not yet in the code:

1. derive PAGE from the route tree instead of parsing the table below;
2. downgrade unknown TYPE / FUNCTION words from failure to warning.

Until they land, the table below is still hand-maintained and still enforced
strictly. That gap is recorded in [Governance](#governance) rather than
pretended away — **a document that describes an intention as though it were
reality is worse than one that admits the difference.**

To add a SECTION or TYPE word today: add it to this file. Do **not** add it to
the code first, and do **not** edit the archived spreadsheet — see
[Where the convention lives](#where-the-convention-lives--corrected-2026-07-29).

## Reference identifiers — `H-nn`, `DQ-nn`, `OQ-n`, …

The repository carries nine separate ID schemes across its documents. One rule
governs all of them:

> **An identifier that is not unique across the repository is not an
> identifier.** If `OQ-1` can mean three different things, then every reference
> to `OQ-1` is ambiguous and the scheme has already failed.

- **Global IDs** live in one owning document and are never reused. `OQ-n`
  (open questions) belongs to [`SUMMARY.md`](../../SUMMARY.md).
- **File-local IDs** must carry a prefix naming their file, so they can never
  collide with a global one.
- Retired IDs are not recycled. A number that once meant something keeps
  meaning it, so old commits and old conversations still resolve.

⚠️ **Outstanding defect, not yet fixed:** `OQ-1` currently means one thing in
[`SUMMARY.md`](../../SUMMARY.md), another in `docs/admin-design.md`, and another
in `docs/features/card-payments.md`.
